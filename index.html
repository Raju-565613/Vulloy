Concepts

Learn

The ideas behind Vulloy, explained plainly — written for the same reason the app was built: to actually understand this stuff, not just use it.

False positive vs. true positive

Think of a motion-sensor alarm. A cat walking by and an actual intruder both trigger the same alarm. The cat is a false positive — a harmless event that looked suspicious. The intruder is a true positive — a real threat correctly caught. Security tools generate mostly false positives; the entire point of this app is separating the two automatically.

Why accuracy alone lies

If 90% of alerts are noise, a model that always guesses "noise" scores 90% accuracy — while missing every real threat. That's why Vulloy always reports recall (% of real threats actually caught) and precision (% of "threat" calls that were right) alongside accuracy. A missed threat is far more costly than an extra false alarm, so recall matters most here.

Precision, recall & F1 — the formulas

Precision = TP / (TP + FP)
Recall = TP / (TP + FN)
F1 = 2 × (Precision × Recall) / (Precision + Recall)

TP = true positive, FP = false positive (false alarm), FN = false negative (missed threat). F1 balances the two into one number when neither alone tells the full story.

How the classifier actually works

The Train Model page runs real logistic regression: every alert becomes a vector of numbers (the 14 features), each multiplied by a learned weight, summed, and squashed through a sigmoid curve into a 0–1 probability. Gradient descent nudges every weight, epoch by epoch, in the direction that reduces prediction error — the loss curve you see is that error shrinking in real time.

Why two layers (rules + ML)?

Rules are instant, free, and fully explainable — perfect for obvious cases ("this exact signature fired 800 times, always harmless"). Machine learning handles the fuzzy cases rules can't anticipate. Real security tools combine both for the same reason: explainability where possible, learned judgment where necessary.

Reading the Alert Detail view

Click any row in the Alert Explorer. For rule-decided alerts, you'll see the exact plain-English condition that fired. For ML-decided alerts, you'll see each feature's real contribution to that specific prediction — amber bars pushed it toward "threat," cyan bars pushed it toward "noise." This is the same math the model used, not a simplified approximation.

Vulnerability categories

What the scanner looks for

Critical

SQL Injection

Malicious input designed to manipulate a database query — e.g. ' OR '1'='1 tricks a login check into always succeeding. Fixed with parameterized queries, never string-concatenated SQL.

High

Cross-Site Scripting (XSS)

Injecting a script that runs in another user's browser, often to steal session cookies. Fixed by encoding output and using a strict Content-Security-Policy.

Critical

Command Injection

Input that tricks an application into running OS commands it shouldn't (e.g. ; cat /etc/shadow). Fixed by never passing user input to a shell.

High

Path Traversal

Using ../ sequences to escape an intended folder and read arbitrary files. Fixed by validating paths against an allowlist.

Medium

Open Redirect

A redirect parameter pointed at an attacker's site, often used in phishing links that start on a trusted domain. Fixed by allowlisting redirect targets.

High

NoSQL Injection

Operators like $ne or $where smuggled into a query object to bypass authentication logic in document databases. Fixed by strict input type-checking.

Use your own data?

You can optionally upload a CSV of real alerts or logs you have, and Vulloy will run the same rule engine and trained classifier against it — instead of the synthetic demo data.

  • Your file is parsed entirely in this browser tab.
  • Nothing is uploaded to any server — Vulloy has no backend.
  • You can switch back to synthetic data at any time.
  • Vulloy cannot and does not access your device, files, or network on its own — you choose exactly what to upload.
